# CLAUDE.md: M365 Graph Cartographer (MGC)

Context for Claude Code. Read this before changing anything.

## What this is

M365 Graph Cartographer (MGC) is an interactive expanding-ring map of Microsoft Graph for Microsoft 365 practitioners (data security architects, admins), not developers. Graph sits in the middle, services (workloads) are on the first ring, sub-services on the second and APIs (resources) on the third; one branch opens at a time. Links show the relationships between APIs. Hover shows a short card (endpoint, least-privileged permissions, main limitation); click opens full notes in a side panel.

The owner is a Microsoft Purview / data security architect. The tool is meant to be public community content as well as a client-facing reference. Write in UK English with plain, direct sentences.

A published copy of v0.1.0 exists as a Claude artifact. The source of truth is now this repo.

## Why we built it rather than reusing something

Existing tools we reviewed on 14 Nov 2026:
- **Graph Atlas MCP** (darrenjrobinson, MIT): a D3 force graph of entity types, permissions and roles, but it only runs inside an MCP host with MCP Apps support. It focuses on Entra and identity schema change tracking and has no documented hover notes.
- **Graph Permissions Explorer** (Merill Fernando): maps permissions to APIs, in tables. Good data source.
- **Graph X-Ray** (Merill): a browser extension that turns admin portal clicks into Graph calls. Not a map.
- **Graph Explorer**: a query tool with no relationship map.
- **Generic OData CSDL visualisers**: the full Graph schema is thousands of types, which is unreadable.

Our angle: a single shareable page, curated rather than a raw schema dump, with practitioner notes (licensing, limitations, gaps outside Graph), kept honest by a scheduled schema scan.

## Architecture

```
data/curated.json   hand-written content
data/placement.json hand-written rules: which Graph areas the generated tier covers, and where each entry goes
scanner/scan.py     stdlib-only: v1.0 + beta $metadata -> data/graph-map.json + data/changelog.json + data/coverage.json + data/generated.json
scanner/generate.py stdlib-only: the generated tier (paths, variants, catalogue permissions, Learn links, placement)
scanner/build_page.py   web/template.html + graph-map.json -> dist/index.html (data embedded)
function_app/       Azure Function (Python v2 model): weekly timer + POST /api/scan -> $web static site
.github/workflows/scan.yml   live host: weekly Actions run -> commit data + GitHub Pages
scripts/scenarios/  one read-only PowerShell script per scenario (Phase 7); scripts/allowlist.json lists the read calls that use POST
tests/              unittest + small CSDL fixtures (v1.xml, beta.xml, v1_later.xml); check_scripts.ps1 checks the scripts against the Graph PowerShell SDK
```

Rules to keep:
1. **Curated and generated data stay separate.** The scanner never writes `curated.json` or `placement.json`.
2. **Standard library only** in `scanner/`, so it runs identically locally, in Actions and in Functions. The Function wrapper alone may use `azure-*` packages.
3. **The core scan is anonymous** (`$metadata` is public). The permission check is optional and needs a token with `Application.Read.All`.
4. **One self-contained page.** No runtime fetches, so it works as a static site, a file, or an artifact (whose CSP blocks external fetches).
5. **The page holds no tenant data**, so public hosting is fine.

## Data model (curated.json)

- `workloads[]`: `id`, `label`, `short` (short name on the ring), `colour`, `family` (`identity`, `collaboration`, `security` or `ai`; the colour is a shade of the family's hue), `summary`, `limits[]`, `docs`, `subservices[]` (ordered `{id, label}`; ids are unique within the workload), optional `phase: 2`. Optional `planned: true`: a service added before its APIs are mapped; its sub-services may be empty (the build allows it), the page draws it hollow and dashed ("Not mapped yet") and shows all its sub-services.
- `hub`: the Graph centre node.
- `nodes[]`: `id`, `label`, `workload`, `subservice` (one of its workload's sub-service ids), `entityType` (fully qualified, for example `microsoft.graph.driveItem`), `path`, `summary`, `permissions.{delegated,application}`, `licence`, `limits[]`, `mapping[]`, `docs`. Optional: `phase: 2`, `tier: "generated"` (an entry built from the schema rather than written by hand; from Phase 2 of `docs/plan-map-all-graph.md`; coverage counts it as mapped but not curated), `kind: "gap"` (outside Graph), or `kind: "operation"` + `action` (for example `runHuntingQuery`). Optional `covers[]` (fully qualified types the node documents alongside its own, such as file plan templates; coverage counts them as on the map) and `legacy[]` (`{path, note, replacedBy}`: an API not to build on; the page shows a "Legacy API" badge and a "Don't build on" section; a test requires a path plus replacedBy or a note).
- `scenarios[]`: `id` (ASCII letters, digits and hyphens; it goes in the hash as `#scenario-<id>`), `label`, `group` (`Classic`, `AI`, `Purview` or `Cost and hygiene`), `summary` (why it matters, one sentence), `licence`, `steps[]`. A step is `{node, do}` plus optional `call`, `permission`, `licence`, `note` (the gotcha), `ps` (its Microsoft Graph PowerShell, read-only; checked by `tests/check_scripts.ps1`) or `psNote` (why it has none, for steps that change data); each defaults to the node's own `path`, permissions, `licence` and first limit. `or: true` makes a step an alternative to the one before it (same number, for example "Drive item / Message"). A test fails if a scenario references a missing node, has no steps or has a bad id. Optional `seeAlso[]` (other scenario ids, shown as links under the steps) and `seeAlsoNote` ({id: text}) to say why, for example that the legal hold comes before access is removed.
- **Generated tier** (Phase 2 of `docs/plan-map-all-graph.md`): `scan.py` writes `data/generated.json`, one line per entry, for every v1.0 entity type that a top-level root reaches (shortest containment path, the type's own area's root first, `{id}` after collections, casts such as `/mobileApps/{id}/microsoft.graph.mobileLobApp/contentVersions` for navs declared on derived types). A type no root reaches folds into its nearest reachable ancestor as a variant (`variants[]`, for example 8 compliance-policy platforms); a type with no reachable ancestor keeps an entry with no path. Entry fields: `id` (`gen-<type>`), `label` (from the type name), `entityType`, `tier: "generated"`, `area`, `path`, `itemPath`, `altPaths[]`, `variants[]`, `ops.{actions,functions}`, `links` (schema relationships to other entries), `scan` (same shape as curated nodes), `permissions` and `permissionsPath` (from Microsoft's catalogue, see below), `docs` (a Learn resource page, only when exactly one file fits). No summary, licence or limits are ever generated.
- **Permissions catalogue:** `permissions/new/permissions.json` in `microsoftgraph/microsoft-graph-devx-content`, read at the repository's HEAD commit (from git's public refs endpoint, not the rate-limited REST API) and pinned in `generated.json` meta and `meta.scan.permissionsCatalogue`. For each entry the scanner takes the GET entry for its item path, then its collection path, then its other paths, and keeps every name marked `least=` for DelegatedWork and Application, in name order: the catalogue often marks Read and ReadWrite both as least (106 of 129 Intune entries), and the code doesn't choose. The page labels them "generated, not checked". If the file's shape changes, `check_catalogue_shape()` refuses it and the previous permissions are kept with a warning. The Learn index (file names in `microsoftgraph/microsoft-graph-docs-contrib/api-reference/v1.0/resources`) needs two REST API calls; set `GITHUB_TOKEN` to lift the anonymous limit of 60 calls an hour, or pass `--docs-index` a saved index. Tests never touch the network (`build_map(fetch_github=False)` by default).
- **Placement** (`data/placement.json`): `areas` lists the Graph areas whose types go on the map; since Phase 3 it is `["*"]` (every area, so a new area that no rule places fails the build). `rules` send entries to `<workload>/<subservice>` by `type`, then the longest `path` prefix (segments, `{id}` ignored, `*` allowed), then `namespace`, then `name` (a glob on the short type name, for types with no path), then `area`. Paths that containment doesn't give fall back to a bound operation (`/copilot/.../getAllEnterpriseInteractions`) or a plain relationship.
- **Beta-only tier** (Phase 3): `build_beta_entries()` builds entries for beta-only types from the beta schema (status "beta only", no Learn link). A beta-only type whose nearest reachable ancestor is a v1.0 entry folds into it as `betaVariants[]`. Unplaced beta types are reported (`unplacedBeta`) but don't fail the build. On the page they are hidden until Filter › Beta-only APIs (generated) is on; picking one from search turns it on. Curated beta-only nodes always show. A curated node overrides the generated entry for its `entityType` or `covers[]` and inherits its variants. **Build rule:** `build_page.py` fails if any type in a listed area is not placed, if a rule points to a missing sub-service, or if there is no generated data yet. `--no-scan` reapplies placement to the last `generated.json`, so extending `areas` needs no new scan.
- `edges[]`: `s`, `t`, `kind` = `nav` (+ `nav`), `ref` (+ `label`, optional `desc` replacing "reference by ID" in the panel, for example "matched by label name, not ID") or `action` (+ `action`). Optional `via` for display, for example `planner/plans`.

The scanner adds `node.scan` (`of`, the type it describes, then status v1.0 / beta only / not found, plus props, navs, betaOnlyProps, betaOnlyNavs and baseTypes), `node.permCheck`, `edge.scan`, discovered edges (`kind: "discovered"`; navs in `DISCOVERY_SKIP_NAVS` (`createdByUser`, `lastModifiedByUser`, `createdBy`, `lastModifiedBy`) are never discovered), `recentChanges` and `state.permissionNames`. `build_page.py` strips `state` before embedding.

Coverage (`data/coverage.json`, never embedded): `parse_csdl` also reads EntityContainer EntitySets/Singletons (`Schema.roots`) and `ContainsTarget` navs. `assign_areas` puts each entity type in the area of the nearest top-level root that reaches it through containment (derived types included), with ties broken by `AREA_PRIORITY`; broad hubs (`users`, `groups`, `me`) lose ties and `/directoryObjects` only gets what nothing else reaches. Then, for what containment misses (Phase 3): a type returned by a bound function or action takes its binding type's area (for example `aiInteraction` -> copilot), then a type reached by a plain relationship (for example `sites/{id}/analytics`), then an abstract base takes its derived types' most common area. Navs and return values typed as `entity` (`BROAD_TYPES`) are ignored. Only 14 v1.0 types stay `unrooted`; placement rules place them by type. The file holds per-area counts, the names of types not on the map, and a `types` index (fq -> area, status) that the next scan diffs for "New in Graph" entries (new v1.0 types, promotions from beta, new roots). `recentChanges` keeps at most `NEW_IN_GRAPH_RECENT` (5) of each kind plus a summary line; `changelog.json` (now up to 2,000 entries) keeps them all. `graph-map.json` gets `coverage` with counts only, and `--no-scan` recounts it from the previous `coverage.json`. A Purview lens (`PURVIEW_SOLUTIONS`, name patterns, first match wins) tags types as Information protection, Records, eDiscovery, Audit, Privacy or Data security API, and `coverage.purview` holds per-solution counts (names in coverage.json). Defender's `security.caseManagement.*` is deliberately not Purview.

## Page (web/template.html)

- Vanilla JS and SVG, no libraries, one self-contained page. The data is injected at the marker `/*__GRAPH_DATA__*/null`. Desktop only (1280 px and up); below 1,000 px the page shows one message saying it is designed for desktop.
- **Shell:** one header row: MGC, a segmented control (Explore · Scenarios · Coverage), search, Filter and Reset. A breadcrumb sits above the map and every crumb is clickable. The key (bottom left of the map) only lists what is switched on.
- **Expanding ring:** R1 = 175 (services), R2 = 292 (sub-services), R3 = 405 (APIs), hub radius 44. Start state: the services evenly spaced on R1 in family order (16 services), bubble area proportional to API count (`svcR`, capped at `SVC_CAP` = 14 APIs, radius 32, so 16 bubbles fit on R1; the key says so when a service is over the cap), count inside, name outside, one satellite dot per sub-service, a dashed guide circle. Opening a service gives it 170° (the others shrink to 12 px bubbles with short names and share the rest) and turns the ring so it points right; its sub-services fan out on R2. Opening a sub-service gives it a wider share of the parent's arc, fans its APIs on R3 and turns the ring again so the sub-service points right. One branch is open at a time in Explore.
- **Crowded sub-services:** an open sub-service shows at most `CAP` = 8 bubbles on R3 (`ringApis()`): curated entries first in curated.json order, then generated ones by number of links. With more than 8, the ring shows 7 and a hollow "+n more" bubble (key `mor:<w>/<s>`, label clickable), which opens a searchable, sortable list (ring order, name, most links, status) in the panel with the cursor in its filter box; picking a row selects that API, and a selected API that would be left off takes the last slot. Links to an API that is only in the list land on the sub-service with a "→ API name" tag. No real sub-service has more than 5 APIs yet, so this was checked with a throwaway build that adds fake generated entries (`.claude/test/index.html`, git-ignored).
- **State:** `S` = `{view, svc, sub, sel, hover, scen, step, preview}`; `F` = filters. `layoutExplore()` and `layoutScenario()` return a target `{a, r, size, mode, lab}` per key (`hub`, `svc:<w>`, `sub:<w>/<s>`, `api:<id>`); `relayout()` tweens angle and radius over 250 ms (no tween with `prefers-reduced-motion`), folds hidden items into their parent, and fits the drawing's bounding box to the map (scale 0.55 to 1.3). The user can still pan and zoom.
- **Labels never overlap or leave the drawing:** labels are anchored outward by angle (`labelAt`) and measured with a canvas, and `resolveLabels()` moves a label out in 13 px steps when it would hit a bubble or another label. Scenario rings try every rotation in 4° steps and keep the one with the fewest overlaps, then the largest fit. An open sub-service's label sits above its bubble and moves outward (right) when the service bubble is in the way. `MGC.check()` in the browser console walks every Explore state and every scenario and returns any overlaps (bubbles are compared as circles, labels as boxes); at 1440×900, 1280×800 and 1280×720 it returns none in all 92 states, and the rendered text boxes agree at 1280×720.
- **Links:** only drawn for the hovered or selected API, unless Filter › All links is on. One accent colour (brick): solid for nav and action, dashed for ref, dotted for scanner-found. A link to an API that isn't on the ring lands on its deepest visible ancestor with a "→ API name" tag; clicking the tag opens that path.
- **Scenarios** use the same ring. Clicking one in the list starts it; hovering or focusing a row does nothing (changed 28 Nov 2026 at the owner's request; before, hovering previewed the route). A dropdown above the list (and at the top of a running scenario) lists every scenario by group; choosing one starts it, and "Choose a scenario…" goes back to the list. Every service and sub-service holding a step opens (the only time several branches are open); other services stay small. Sub-services with steps are pills, the rest are dots (name in the hover card). Only step APIs show on R3, with step-number badges on the inner side. Steps under 50° apart are joined by a short arc just outside the ring (API labels sit 16 px further out to leave a channel); longer jumps curve through the middle. Done steps are solid with filled numbers, the current step has a halo, steps to come are dashed; a preview is all dashed. The panel walks the steps (Back, Next, Step n of m, Exit scenario). Each step shows its call with an HTTP / PowerShell switch (remembered in localStorage as `mgc-code`) and a Copy button; each scenario has a "Download script" button for its read-only script (embedded by `build_page.py --scripts`, default `scripts/scenarios`, as `D.scripts[id] = {text, tested}`; downloaded from a Blob; no button when the folder is missing, as in the Azure Function package).
- **Sizes:** service and sub-service bubbles stop growing at 14 APIs (`SVC_CAP`); sub-services can have a `short` ring name (`subservices[].short`, for example "Authentication" for "Authentication methods & strengths"); the panel, hover card and breadcrumb keep the full name.
- **Generated entries** show a dashed "Generated" badge (curated ones a "Curated" badge), a fixed note that no notes have been written, the catalogue permissions with the warning and pin, folded variants, other paths, actions and functions, the schema and the Learn link. On the ring they rank by curated links plus schema links, and labels longer than 34 characters are shortened (the panel has the full name). Search also matches variant type names.
- **Coverage view:** two headline figures, mapped (on the map, either tier) and curated (hand-written entries), from `coverage.onMap` and `coverage.curated`; bars per service (`coverage.services`, from the scanner; solid curated, pale generated, outlined beta only) and per Purview sub-service (Purview solutions mapped to sub-services; the data security API counts under Information protection), plus the full area table.
- **Filters:** workloads, All links, API status (beta-only and legacy rings, on by default), Outside Graph diamonds (on by default), Changed this week (status, property and relationship changes in the 7 days up to the last scan; new nodes don't count; read from `changedNodes`, which the scanner keeps apart from the 60-entry `recentChanges`), Links found by the scanner (reviewers). Reset returns everything to the start state, clears the hash, and shows a dot whenever anything differs from the start.
- **Hash routing:** `#<nodeId>` opens its service and sub-service and selects it; `#svc/<workload>` and `#svc/<workload>/<subservice>` open a branch; `#scenario-<id>` starts a scenario.
- **Keyboard:** every bubble and tag is focusable with a visible focus ring; Enter opens or selects; Escape steps back one level; arrow keys move between siblings.
- Nodes with no valid sub-service show under a temporary "Unsorted" sub-service (`_unsorted`).
- Pointer input: only the primary mouse button (or touch/pen) starts a pan or select. `endGesture()` clears the gesture on lostpointercapture, contextmenu, the pointer leaving the window, window blur and the tab being hidden, and a mouse move with no buttons held ends a drag.
- Design: the "Planning office" palette (stone #e7e4df, ink, brick #c8371e, white panels; night #171513), Schibsted Grotesk. Light and dark both work, including via `data-theme` on the root.

## Commands

```bash
python -m unittest discover tests          # must pass before any commit
pwsh -NoProfile -File tests/check_scripts.ps1   # SDK checks on the scenario scripts (the tests run it when PowerShell 7 and Microsoft.Graph are installed)
python scanner/scan.py                      # live scan (needs graph.microsoft.com)
python scanner/scan.py --no-scan            # re-merge curated and placement edits, keep last scan results
python scanner/scan.py --offline            # scan without reading the permission catalogue or Learn index from GitHub
python scanner/build_page.py                # writes dist/index.html; fails if the sub-service structure is broken
python scanner/build_page.py --allow-unsorted   # build anyway when some nodes have no sub-service yet (shown under "Unsorted")
cd function_app; ./package.ps1              # Windows (package.sh on bash): copies scanner/data/web in before `func azure functionapp publish`
```

To check the page visually, open `dist/index.html` in a browser. Test at a desktop width (around 1440×900) and a phone width (around 390×844), in light and dark modes.
